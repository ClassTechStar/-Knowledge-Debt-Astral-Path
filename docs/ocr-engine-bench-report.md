## 一、结论速览

1. **RapidOCR（本地仓库 `python/` 包，v3 线，3.9.3.dev16，PP-OCRv6 检测/识别模型）全面胜出，已集成至项目生产管线**（`tools/ocr_pipeline.py`），页级多线程并行，测试全绿。
2. 速度（120 抽样页基准，多进程并行）：**rapid3 1.45 页/s** ≈ 3.5× 项目原用 rapidocr_onnxruntime 1.4.4（0.41）≈ **13.9× PaddleOCR 3.7**（0.105，PP-OCRv6 medium 模型）。
3. 质量：三家基本持平（vs 文本层 CER 0.36–0.37）；文本层完好书上 rapid3 页级 CER 中位数 **0.5%–2.1%**；字符级混淆均为经典形近对（I/l/1、巾/中、山/出、日/目），频次极低。
4. PaddleOCR **不集成**：同质量下慢一个数量级；且其 `enable_mkldnn=True` 在 paddle 3.3.1 + PP-OCRv6 模型上直接抛 `NotImplementedError`（paddle 侧 bug），无可用加速路径。
5. 并行性的诚实结论：CPU OCR 在本机受**内存带宽**约束，吞吐上限 ~1.3–1.6 页/s；超过 ~4 个并发 worker 后收益≈0（见 §5）。多核多线程实现仍有价值：多文件并发、可调、低延迟尾部。

## 二、测试设置

- 引擎：
  - `rapid3` = 本地 RapidOCR 仓库 `python/` 包（未改动仓库，`pip install --no-deps` 安装副本），v3 线，默认 PP-OCRv6 模型

## 五、并行性实测（多核多线程的真实收益）

8 页同书探针（rapid3）：

| 配置（worker×intra） | 吞吐（页/s） | 备注 |
|---|---|---|
| 1×1 | ~0.7 | 串行下限 |
| 1×8 | **1.29** | 单进程 8 线程已达上限 |
| 1×16 | 0.98 | 线程过多反而退化 |
| 2×8 | 1.22 | |
| 4×4 | 1.11–1.45 | 全量跑实测均值 1.64 |
| 8×2 / 12×1 | 0.93–1.07 | 无增益 |

结论：**CPU OCR 受内存带宽约束，单进程 8 线程即封顶；更多进程不增加吞吐**。生产集成采用 4 线程（每线程独立引擎、单实例 intra=2）：吞吐接近上限、内存占用低（4×~250MB）、多文件并发时仍可水平占用余核。
