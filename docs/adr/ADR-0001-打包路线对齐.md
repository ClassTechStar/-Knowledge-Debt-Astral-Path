# ADR-0001 · Windows / Android 打包路线对齐

- 状态：**已接受（Accepted）**
- 日期：2026-09-26
- 关联：审计缺陷「文档承诺 MSIX + AAB + NativeAOT（§11/§12），现状是 Inno Setup EXE + 签名 APK（§32）」；《分工矩阵》§8.7「商店签名 APK / EXE · P4」

## 背景

技术方案客户端篇（§11–§12）承诺的桌面/移动交付形态是 **Avalonia + SkiaSharp + NativeAOT 的 MSIX** 与 **net10.0-android 的 AAB**；而 2.2.0 实际发布物是：

- Windows：`AstralPath-Monolith-Setup-2.2.0.exe`（WinForms + WebView2 壳 + Inno Setup，`setup-monolith.iss`）
- Android：`AstralPath-Android-2.2.0-Store.apk`（Kotlin WebView 壳，`com.astralpath.app.v22`，minSdk 26 / targetSdk 35）

两者共享同一份 `index.html`（三端 md5 门禁 + `sync-monolith-html.ps1`），业务全部在页面内完成。

## 决策

1. **2.2.x 竞赛交付线维持 Inno Setup EXE + 签名 APK**，不再追赶 MSIX/AAB。理由：
   - 两个壳合计 < 500 行代码，是当前最薄、故障面最小的交付形态；演示门禁（冷启动、离线可用、断网兜底）实测满足。
   - MSIX 需要签名证书与打包流水线；AAB 需要Play 管理 restrinctions，两者对当前演示场景零增益。
   - 「三端一份 index.html」的同源纪律（md5 门禁）比打包格式更接近本项目的核心风险。
2. **MSIX / AAB / Avalonia+SkiaSharp 原生端推迟到「原生端重构阶段」**，与 §12 的 400 节点 60fps 图谱、§13 的边列表原生页一并评估。启动条件：
   - 需要商店分发或企业侧加载（MSIX 的 PowerShell 受限模式 / AAB 的按设备交付）时；
   - 或单文件 HTML 的性能门禁（大教材渲染、WASM OCR）在目标设备上实测不达标时。
3. **文档口径修正**：§11–§13 的 MSIX/AAB/NativeAOT 章节按「目标态（重构阶段）」阅读；「交付态」以本文与本节为准。`AstralPath.Desktop` 项目名保留，但当前实现为 WebView2 壳（App.axaml 等 Avalonia 文件已弃用），以 `csproj` 为准。
4. 每次发布仍执行既有门禁：`sync-monolith-html.ps1`（三端 md5 + C3 哨兵）→ `verify_all.ps1` 全绿 → Inno Setup 编译 → APK 签名构建。

## 后果

- 正面：消除「文档说 A、仓库是 B」的双口径；打包维护成本维持最低。
- 负面：Windows 商店 / Google Play 分发暂不可用（当前无此需求）。
- 回退：若分发需求出现，按启动条件立项，走 ADR-0002。
