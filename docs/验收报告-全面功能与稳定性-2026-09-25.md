## 三、P1 · 高（影响可用性与数据可信度）

### P1-1 畸形 JSON 触发 500 —— 4 个接口（含登录）

**描述**
`[FromBody]` 参数为非可空类型且方法内无 null 检查，而启动时设置了 `SuppressModelStateInvalidFilter = true`（`ApiBootstrapper.cs:60`）关闭了框架的自动 400，导致模型绑定失败后参数为 `null`，随即解引用崩溃。

**复现步骤**
```bash
curl -i -X POST http://127.0.0.1:5190/v1/attempts \
     -H "Content-Type: application/json" -d '{bad'
```
**实际结果**：`HTTP 500`
```json
{"data":null,"error":{"code":"INTERNAL_ERROR","message":"服务内部错误，请稍后重试",
 "details":{"type":"NullReferenceException"}},"traceId":"..."}
```
**实测受影响接口**

| 接口 | 非法 JSON | 空对象 `{}` |
|---|---|---|
| `POST /v1/attempts` | 500 | 400（有字段校验） |
| `POST /v1/debt-edges/sale-check` | 500 | — |
| `POST /api/v1/auth/register` | 500 | — |
| `POST /api/v1/auth/sessions`（**登录**） | 500 | — |

**影响范围**
任意客户端（含恶意构造）可用一条畸形请求换来一次 500 与一段异常堆栈写盘；**登录接口**中招，用户侧只看到"服务内部错误"，无法自助恢复。26 个 `[FromBody]` 接口中仅 11 个做了 null 保护，**同类隐患至少还有 4 处未逐一验证**。

**根因（含精确位置）**
```
src/AstralPath.Api/Controllers/CoachProgressController.cs:135
  at ...CreateAttempt.b__0()      ← request.StudentId 解引用 null
```
堆栈已由全局异常中间件打印到控制台：`[AstralPath] unhandled POST /v1/attempts: System.NullReferenceException`。

**修复建议**
```csharp
// 方案 A（推荐，逐接口）：在解引用前兜底
public IResult CreateAttempt([FromBody] CreateAttemptRequest? request)
{
    if (request is null)
        return HttpResults.Fail(400, ErrorCodes.ValidationError, "请求体必须是合法的 JSON 对象");
    ...
}

// 方案 B（全局，防止再犯）：自定义 ProblemDetails / 模型绑定失败过滤器，
// 在 SuppressModelStateInvalidFilter 之外补回统一 400 形状
builder.Services.Configure<ApiBehaviorOptions>(o => {
    o.InvalidModelStateResponseFactory = ctx =>
        HttpResults.Fail(400, ErrorCodes.ValidationError, "请求体格式错误",
                         ctx.ModelState.ToDictionary(k => k.Key, v => v.Value?.Errors.FirstOrDefault()?.ErrorMessage));
});
```
**验收标准**：上表 4 个接口在畸形 JSON / 空 body / 全 null 三种输入下均返回 **400 + 统一 `{data,error,traceId}`**，服务端 `unhandled` 计数为 0。

**优先级**：`P1`

### P1-2 运行时数据重启即丢（持久化配置是死配置）

**描述**
`appsettings.json` 声明 `Persistence:Mode = "postgres"`，但 **Api 工程从未引用 `AstralPath.Persistence`、从未读取 `Persistence:` 配置段**，实际只用内存 `AstralPathStore`。启动日志、`/health/ready`、`/v1/modules/status` **均不报告真实持久化模式**。

**复现步骤**
```bash

curl -s http://127.0.0.1:5190/v1/modules/status      # students=3 kbDocs=3 agentTurns=42
curl -s -X POST http://127.0.0.1:5190/v1/attempts -H "Content-Type: application/json" \
     -d '{"studentId":"persist-check-student","kpId":"K12","questionId":"Q1","correct":true,"selfConf":5}'
# 2) 重启进程（Stop-Process → dotnet run）
# 3) 复查
curl -s http://127.0.0.1:5190/v1/modules/status      # students=2 kbDocs=0 agentTurns=0
curl -s http://127.0.0.1:5190/v1/profile/persist-check-student
```
**实际结果**

| 指标 | 重启前 | 重启后 |
|---|---:|---:|
| students | 4 | **2**（仅剩代码 seed 的演示学生） |
| kbDocs | 3 | **0** |
| agentTurns | 42 | **0** |
| 新增学生 | 可查 | `RESOURCE_NOT_FOUND` |

**影响范围**
学生作答、掌握度、知识库文档、智能体会话**全部不可恢复**；与方案 §0.2「PostgreSQL + pgvector 持久化基线」直接冲突。
值得注意：**无服务单体版（localStorage）反而比"全功能版"更持久**——这是产品定位上的倒挂。

**根因**
```csharp
// ApiBootstrapper.cs 服务装配段：只有内存实现
var store = new AstralPathStore(graphPack);
builder.Services.AddSingleton(store);          // ← 无 AddAstralPathPersistence
```
对比 `services/*-svc/Program.cs` 均已正确接入：
```csharp
ServiceHost.Run<DiffusionController>(args, "concept-diffusion-svc",
    b => b.Services.AddAstralPathPersistence(b.Configuration));
```
**两种部署形态的持久化能力不一致。**

**修复建议**
```csharp
// ApiBootstrapper.Build 中补上（与微服务同源）
builder.Services.AddAstralPathPersistence(builder.Configuration);
// 并把实际模式暴露到健康检查
app.MapGet("/health/ready", (IConfiguration cfg) => Results.Json(new {
    status = "ready",
    persistence = cfg["Persistence:Mode"],          // ← 新增
    connection = cfg.GetConnectionString("Default") is null ? "memory" : "configured",
    checks = new { graph = "ok", ... }
}));
```
同时在**启动时**打印一行明确的降级告警：
```csharp
if (postgres 不可达 && AllowMemoryFallback)
    Console.WriteLine("[WARN] PostgreSQL 不可达，已降级为内存模式；进程重启将丢失全部数据。");
```
**验收标准**：① 停止 PostgreSQL 后启动，日志出现显式降级告警；② `/health/ready` 含 `persistence` 字段；③ PostgreSQL 可用时写入 → 重启 → 数据仍在。

**优先级**：`P1`

### P2-1 全站无鉴权与越权保护

**复现步骤**（无需任何令牌）
```bash

curl -s -X POST http://127.0.0.1:5190/v1/attempts -H "Content-Type: application/json" \
     -d '{"studentId":"demo-student-b","kpId":"K12","questionId":"Q1","correct":true,"selfConf":5}'  # 201
```
**实测结果**：以上全部成功。持 A 学生令牌读取 B 学生画像同样 200（令牌不绑定主体）。

**影响范围**
任何人可读写任意学生数据、查看教师端聚合、**篡改 consent 授权状态**（而 consent 是产品的核心伦理承诺）。与方案 §6.4「consent-svc：教师可见性**服务端强制**」、URGENT 义务 §6.4 直接冲突。

**根因**：全工程 `UseAuthentication` / `UseAuthorization` / `[Authorize]` **零出现**；`AuthStore` 仅用于签发令牌，未参与任何校验。

**修复建议**
1. 接入 ASP.NET Core 认证（Bearer）+ 最小授权策略：
   `builder.Services.AddAuthentication().AddBearerToken();`
   `builder.Services.AddAuthorization(o => o.AddPolicy("student-self", p => p.RequireClaim("role","student")));`
2. 给「本人资源」路由加资源级校验（`userId == route.studentId`），越权返回 **403**
3. 教师端路由强制 `role in {teacher, admin}` 且**叠加 consent 校验**（服务端）
4. 演示模式可保留匿名，但必须用**显式开关**（如 `ASTRALPATH_ALLOW_ANONYMOUS=true`）并在日志与大屏上标注，而不是默认全开

**优先级**：`P2`（若定位为校内真实使用则升为 `P1`）

**先修正自己**：复验时发现原报告把「consent 未做服务端强制」说重了——
`TeacherConsentGraphController.Hotspots` **本来就**做了 fail-closed 的 consent 校验

`Grant`/`Revoke` 的 actor 取自请求体（`request.ActorId`），客户端自报身份即可伪造。

**改动**（`ApiBootstrapper` 新增访问控制中间件 + 4 个配置开关）

3. **consent 主体不可伪造**：`Grant`/`Revoke` 已登录时**以令牌主体为准，忽略请求体 ActorId**（`ResolveActor`）
4. **可选强制登录**：`Security:RequireAuth=true` 时 `/v1/**`（除 `/v1/demo/*`）必须持有效令牌 → 401
